Отталкиваюсь от того, что уже есть в smetadoma05: это CRM «агент → менеджер → сделка», а не витрина. Ключевые сущности:

Customer — лид/клиент в CRM (телефон, паспорт, агент-владелец)
Project — сделка клиента
Specification — смета с габаритами, строками, total_amount, КП/договор
HouseSpecificationTemplate + HouseTemplate — внутренний шаблон расчёта (номенклатура, qty_basis), не карточка товара для покупателя
Ниже — предлагаемая архитектура и вопросы.

Главная идея: три слоя, не один
┌─────────────────────────────────────────────────────────────┐
│  ПУБЛИЧНЫЙ КАТАЛОГ (как Ozon/WB)                             │
│  /houses/{slug}  — без входа, SEO, шаринг ссылки             │
└───────────────────────────┬─────────────────────────────────┘
                            │ «Собрать / Заказать / В ЛК»
┌───────────────────────────▼─────────────────────────────────┐
│  КОНФИГУРАТОР + КОРЗИНА / ЧЕРНОВИК КОНФИГУРАЦИИ              │
│  выбор: брус 145, крыша, электрика, размер 8×10…             │
└───────────────────────────┬─────────────────────────────────┘
                            │ конвертация (агент / клиент / авто)
┌───────────────────────────▼─────────────────────────────────┐
│  CRM (уже есть)                                              │
│  Customer → Project → Specification (+ КП, договор)            │
└─────────────────────────────────────────────────────────────┘
                            ▲
┌───────────────────────────┴─────────────────────────────────┐
│  ЛК КЛИЕНТА (отдельный вход, не AuthUser)                    │
│  мои конфигурации, привязанные спецификации, статус сделки   │
└─────────────────────────────────────────────────────────────┘
Не стоит напрямую отдавать публичную карточку из Specification или HouseSpecificationTemplate: там слишком много внутренней кухни (строки сметы, скидки агента, служебные поля). Каталог — отдельная «витрина»; спецификация — «снимок расчёта» после выбора.

Сценарии:

Гость на витрине → собрал → «Оставить заявку» → создаётся Customer + configuration + уведомление агенту.
Клиент в ЛК → сохраняет конфигурации → агент конвертирует в Specification.
Агент в CRM → «Создать из каталога» → та же конфигурация → Specification.
Конвертация в Specification (важно переиспользовать код)
Сервис configuration_to_specification:

Берёт house_spec_template_id продукта.
Копирует HouseTemplate → SpecificationItem (у вас уже есть похожая логика при создании спецификации).
Применяет опции: меняет номенклатуру/количества/добавляет пакеты «электрика».
Подставляет габариты из конфигурации.
Записывает specification_id в конфигурацию.
Так не дублируете расчёт — каталог только выбирает параметры, смета остаётся источником истины для КП и договора.

3. ЛК клиента (отдельно от CRM)
Сейчас AuthUser — это сотрудники. ЛК нужен отдельный контур:

portal_user (или customer_account)
customer_id → customers.id (1:1 или 1:N если семья)
phone / email, password_hash или только OTP/SMS
is_verified
Вход: телефон + код / пароль (как вы уже делаете логин по email для агентов).

В ЛК клиент видит:

список house_configuration (черновики и готовые)
привязанные Specification (read-only: сумма, статус, ссылка на КП PDF если разрешено)
статус Project / этапы (упрощённо, без внутренних комментариев агента)
не видит: номенклатуру построчно, маржу, служебные поля
Связь с CRM: Customer уже есть — ЛК просто даёт клиенту доступ к своим записям по customer_id. Агент по-прежнему ведёт сделку в CRM.

Не делать	Почему
Публиковать Specification напрямую
утечка цен, скидок, внутренних строк

Сразу строить полноценный checkout
достаточно «заявка / бронь / звонок менеджеру» на первом этапе
6. Поэтапный план
Этап 1 — витрина (MVP)
Каталог + карточка + slug + фото. Без ЛК. Кнопка «Получить расчёт» → форма (имя, телефон) → Customer + задача агенту.

Этап 2 — конфигуратор
Группы опций, расчёт «от …» / estimated_total, ссылка /c/{token}.

Этап 3 — конвертация в Specification
Кнопка агента «Создать смету из конфигурации».

Этап 4 — ЛК клиента
Вход по телефону, список конфигураций и привязанных спецификаций.

Этап 5 — углубление
Сравнение комплектаций, избранное, уведомления, оплата (если нужно).

7. Фронтенд
Разумно отдельный роутинг, не внутри Gentelella CRM:

/              — лендинг или каталог
/houses        — список
/houses/:slug  — карточка + конфигуратор
/c/:token      — shared configuration
/portal/*      — ЛК клиента
/dashboard     — как сейчас, CRM для сотрудников
Один репозиторий, два «приложения» в Vite (или lazy routes с разным layout).

Вопросы к вам (чтобы уточнить дизайн)
Кто собирает дом в конфигураторе? только клиент, только агент, или оба (агент шлёт ссылку /c/{token})?

Цены на витрине — публичные точные, только «от …», или цена после регистрации/звонка?

Один клиент — много проектов? (дачный дом + баня) — в ЛК показываем все Project или только активный?

Каталог кто наполняет? менеджер в «Настройках» CRM или отдельная роль «контент-менеджер»?

Размеры — фиксированный набор (8×10, 10×12) или произвольные габариты с пересчётом сметы?

Материал (брус 145 vs каркас) — это разные карточки каталога или одна карточка с опцией «тип стен»?

ЛК обязателен для заказа или можно всё через телефон без регистрации (как сейчас лид в CRM)?

Нужна ли привязка к филиалу/менеджеру с каталога (разные цены по регионам)?

Краткий вывод
Каталог — новый слой (catalog_product + опции + медиа + slug).
Конфигурация — промежуточная сущность с публичным token и связью с Specification.
ЛК — отдельная аутентификация, привязка к существующему Customer.
Specification не заменяется, а генерируется из конфигурации — это сохранит КП, договоры и всю текущую номенклатурную логику.
